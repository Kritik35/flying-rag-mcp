# FlyingRAG — Постоянный регламент отчётности Gemini / Antigravity

**Назначение**: Обязательный регламент документирования, тестирования и публикации результатов для агента Gemini / Antigravity при работе над проектом `Kritik35/flying-rag-mcp`.
**Статус**: Действующий постоянный регламент.

---

## 1. Регламент после каждого завершённого этапа

После каждого завершённого этапа разработки, аудита или исправления дефектов агент обязан:

1. **Полный технический отчёт в `reports/`**:
   - Сохранять подробный технический отчёт в каталоге `reports/` под уникальным названием этапа (например, `STAGE4_2_INDEPENDENT_ACCEPTANCE.md`).
   - Фиксировать реальные результаты `PASS` / `FAIL`, выявленные дефекты, воспроизводимые тестовые сценарии и точные номера строк кода.
   - Запрещено указывать статус `CERTIFIED` или `PASSED`, если тестовое покрытие частичное или условия не проверены независимым кодом.

2. **Обновление `reports/LATEST.md`**:
   - Поддерживать файл `reports/LATEST.md` в актуальном состоянии после каждого этапа.
   - Обязательные поля: дата, название этапа (Stage), текущая Git-ветка, предшествующий коммит SHA, Run ID, общий статус, открытые блокеры/риски, ссылки на подробные отчёты и артефакты в `reports/`.
   - Добавлять явную информацию о том, какие именно проверки реально запускались в локальном окружении, а какие зафиксированы по спецификации.

3. **Машинно-читаемая матрица тестов в JSON**:
   - Сохранять результаты тестов в формате JSON (`reports/*_test_matrix.json`, `reports/*_gate_results.json`).
   - Фиксировать реальные статусы `PASS` / `FAIL` каждого отдельного теста с его `test_id` и временем выполнения (`elapsed_ms`), а не только сводное заключение.
   - Контролировать изменения в Git с помощью `git diff --check`.

4. **Криптографическая привязка и аттестация коммита**:
   - Проводить финальное приёмочное тестирование на чистом рабочем дереве (working tree).
   - Фиксировать `tested_commit_sha` и фактический хеш дерева Git (`git rev-parse HEAD^{tree}` или `git write-tree`).
   - Не выдавать хеш предыдущего коммита за хеш тестируемого кода.

5. **Строгая проверка конфиденциальности (Privacy Check)**:
   - Запрещено публиковать или коммитить в Git:
     - Базы данных SQLite (`metadata.db`), векторные хранилища LanceDB, журналы WAL/SHM.
     - API-ключи, токены, пароли, секреты.
     - Исходные нормативные документы заказчиков и первичные файлы корпуса.
     - Персональные локальные пути оператора (директории пользователей Windows/Linux).
     - Сырые тексты поисковых запросов (`query`). В телеметрии и отчётах допустимы только `query_hash` и обезличенные категории/метки.
   - Выполнять автоматизированное сканирование `git diff` на отсутствие утечек перед каждым коммитом.

6. **Изолированная публикация через Git**:
   - Коммитить отчёты вместе с соответствующими изменениями кода только в согласованную отдельную audit-ветку GitHub (например, `audit/stage4-2-verification`).
   - Отправлять изменения стандартным `git push` без флага `--force`.
   - Запрещено выполнять `merge` в `master` или модифицировать `production`.

7. **Честность при отрицательных результатах**:
   - При любых неудачных испытаниях, обнаружении регрессий или сбоях сохранять отчёты с явным указанием статуса `FAILED` или `BLOCKED`.
   - Запрещено скрывать отрицательные результаты, подменять статусы или имитировать успешность непроверенных компонентов.

## 2. Протокол взаимодействия с внешним аудитором (ChatGPT)

- **Основной канал передачи**: GitHub является единственным официальным каналом передачи результатов внешнему независимому аудитору ChatGPT.
- **Порядок аудита**:
  1. Gemini локально выполняет задачу в изолированном worktree, запускает верификацию, формирует отчёты и публикует коммит в GitHub.
  2. Пользователь отправляет ChatGPT запрос на проверку: «Проверь последнюю сборку FlyingRAG».
  3. ChatGPT получает последний коммит ветки через GitHub REST API, читает `reports/LATEST.md` и приложенные отчёты, независимо проверяет исходный код и полноту тестов.
- **Формат финального ответа Gemini в чате**:
  - Краткое резюме статуса (GO / NO-GO / PASSED / FAILED).
  - URL опубликованного коммита на GitHub и его полный 40-символьный SHA.
  - Длинные тексты отчётов и списки тестов в чат не дублируются — они читаются аудитором непосредственно из репозитория.

## 3. Абсолютные запреты (Invariants)

- **NO PRODUCTION WRITES**: Запрещена любая запись в `C:\RAG_Acer\repos\flying-rag-mcp` и рабочие базы.
- **NO REINDEX**: Запрещена переиндексация корпуса без отдельного явного распоряжения.
- **NO MERGE**: Запрещено слияние audit-веток в `master`.
- **NO FORCE PUSH**: Запрещена перезапись истории Git с помощью force push.
- **NO SECRET COMMIT**: Запрещён коммит секретов, сырых запросов и закрытых данных.
