# Бэкап, восстановление и уборка после сбоя

Хранилище — это две части, которые имеют смысл только вместе:

| Часть | Где (по умолчанию) | Что в ней |
|---|---|---|
| LanceDB | `data/lancedb/` | векторы, текст фрагментов, FTS- и ANN-индексы, манифест модели |
| SQLite | `data/metadata.db` | файлы, родительские фрагменты, правила, кэш фрагментов, задания |

Пути берутся из `config.yaml` (`storage.lancedb_path`, `storage.metadata_db`)
относительно `FLYING_RAG_HOME`, если он задан.

Все операции записи — индексатор, наблюдатель, обслуживание, бэкап,
восстановление — идут под общей блокировкой `<lancedb>.writer.lock`. Это
блокировка операционной системы: если держатель упал, она снимается сама.
Индексатор держит её только на время коммита документа (секунды), поэтому
бэкап можно делать при работающих серверах.

## Снимок

```powershell
.\.venv\Scripts\python.exe scripts\backup_store.py backup --dest D:\flying-rag-backups --keep 3
.\.venv\Scripts\python.exe scripts\backup_store.py list --dest D:\flying-rag-backups
```

* Снимок снимается между коммитами: SQLite через online-backup, каталог
  LanceDB копией. После копирования он открывается и сверяется с оригиналом
  (число строк в таблицах, файлов, правил, `PRAGMA quick_check`); результат —
  в `backup.json` внутри снимка. Непроверенный снимок восстанавливать скрипт
  откажется.
* `--keep N` оставляет N последних снимков в этом каталоге, остальные удаляет.
* Без `--dest` снимки ложатся в `data/backups/` — на тот же диск. Это защищает
  от ошибки в данных, но не от потери диска; для настоящего бэкапа укажите
  другой диск.
* Размер снимка равен размеру `data/lancedb/` вместе со старыми версиями.
  Перед бэкапом стоит сжать хранилище (`scripts\db_maintenance.py --apply`):
  после большой переиндексации это обычно в 2–3 раза меньше.

Когда делать: перед любой массовой операцией (доиндексация, `--force`,
дедуп правил, обслуживание) и по расписанию — например, раз в неделю через
Планировщик заданий Windows:

```powershell
schtasks /create /tn "FlyingRAG backup" /sc weekly /d SUN /st 03:00 /tr "\"<путь>\.venv\Scripts\python.exe\" \"<путь>\scripts\backup_store.py\" backup --dest D:\flying-rag-backups --keep 4"
```

## Восстановление

1. Остановите всё, что держит хранилище открытым: MCP-серверы в клиентах
   (Claude Desktop, Claude Code и др.), фоновый `main.py --daemon`, монитор.
   Скрипт проверит это сам и откажется, если найдёт `main.py`.
2. Посмотрите список снимков и выберите нужный:
   `scripts\backup_store.py list --dest D:\flying-rag-backups`.
3. Восстановите:

   ```powershell
   .\.venv\Scripts\python.exe scripts\backup_store.py restore --from D:\flying-rag-backups\store-20261003-030000 --yes
   ```

   Текущее состояние не удаляется: оно отодвигается в
   `lancedb.pre-restore-<время>` и `metadata.db.pre-restore-<время>` рядом
   с оригиналом. После восстановления числа сверяются со снимком.
4. Запустите серверы. Файлы, изменённые после снимка, наблюдатель
   переиндексирует сам при следующем проходе (по sha); можно ускорить
   `reindex_path` по нужной папке.
5. Когда убедились, что всё работает, удалите `*.pre-restore-*`.

## Уборка после сбоя индексации

Индексатор пишет документ атомарно: пока документ разбирается и
эмбеддится, хранилище не меняется; коммит — одна операция LanceDB и одна
транзакция SQLite. Прерванный посередине коммит помечает файл как
`reindexing`, и следующий прогон переделает его, даже если байты не менялись.

Хранилище, записанное прежним кодом, и ручные операции могли оставить
рассогласование. Проверка — только чтение:

```powershell
.\.venv\Scripts\python.exe scripts\store_recovery.py
```

Она показывает:

* незавершённые коммиты — их переделает индексатор;
* остатки документов, файлов которых больше нет на диске, — `--apply` их
  удалит;
* документы, файл которых на месте, а записи в `files` нет, — их нужно
  переиндексировать (`reindex_path` по пути), а не удалять: удаление убрало бы
  их из поиска;
* записи `files` без единого вектора — `--apply` пометит их к
  переиндексации.

`--apply` работает под блокировкой и правила не трогает.

## Правила

Правила (`engineering_rules`) лежат в `metadata.db` и попадают в снимок.
Отдельно их можно выгрузить `backup_rules.py dump` — это нужно перед любым
`--force` по нормативам: такой прогон, если извлечение правил выключено или
не завершилось, оставляет прежние правила, но старые ссылки на фрагменты
могут перестать совпадать.

## Что в снимок не входит

* `data/table_parquet/` — кэш таблиц, пересобирается из исходников;
* визуальное хранилище ColPali (`data/lancedb_colpali`) — выключено;
* исходные документы — их бэкап делается средствами, которыми вы храните
  сами документы.

## Обновление Lemonade

Индекс посчитан одной моделью эмбеддингов в одной сборке llama.cpp. Сверка
контракта на старте сравнивает только имя модели и нарочно не различает
квантизации, а обновление Lemonade может принести новую сборку llama.cpp и
другой файл под тем же встроенным именем (`builtin.Qwen3-Embedding-0.6B-GGUF`
определяется реестром самого Lemonade). Запросы тогда кодируются не так, как
документы, и поиск портится без единой ошибки.

До обновления:

1. Остановить индексацию: наблюдатель (`main.py --daemon`), `reindex_path`,
   ручные прогоны. Индексатор, увидевший недоступный Lemonade, откажется
   писать, но прерванный прогон придётся повторять.
2. Снять отпечаток и копию конфигов Lemonade:

   ```powershell
   .\.venv\Scripts\python.exe scripts\lemonade_fingerprint.py save
   ```

   Пишет `data/lemonade_fingerprint.json` (версия Lemonade, сборка llama.cpp,
   контрольные точки моделей, векторы проб, оценки реранкера) и копирует
   `~/.cache/lemonade/*.json`, `server_models.json`, `backend_versions.json`
   в `data/backups/lemonade-<время>`.
3. Свежий снимок хранилища (`backup_store.py backup`) и замер эталона
   (`rag_eval.py run --repeat 2`), чтобы было с чем сравнивать.

После обновления:

1. Убедиться, что модель эмбеддингов загружается под тем же именем и с теми
   же параметрами (`ctx_size`, бэкенд), что записаны в отпечатке.
2. Сверить:

   ```powershell
   .\.venv\Scripts\python.exe scripts\lemonade_fingerprint.py compare
   ```

   `0` — совпадает; `1` — сдвиг в пределах шума квантизации, перемерить эталон;
   `2` — векторы другие: поиск по старому индексу неверен. Тогда либо вернуть
   прежнюю версию Lemonade (сборку llama.cpp можно закрепить в
   `backend_versions.json`, файл модели — указать явно пользовательской
   моделью), либо полностью переиндексировать в новое хранилище.
3. Перезапустить MCP-серверы и прогнать эталон.

Реранкер чувствителен к физическому батчу llama-server (сейчас 512 токенов на
пару запрос–документ). Если новая сборка его изменит, запросы с длинными
документами начнут получать HTTP 500 «too large»; сервер в этом случае один
раз повторяет запрос с половинным бюджетом и пишет об этом в журнал.
