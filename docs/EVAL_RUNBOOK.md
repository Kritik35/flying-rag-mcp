# Как снять замер качества поиска

Кому: оператору живой машины с Lemonade и проиндексированным корпусом.
Зачем: получить честный baseline, относительно которого можно мерить Волну 1
(RRF вместо линейной комбинации, русский стемминг, exact-guards, калибровка
порогов). Без этого baseline менять retrieval бессмысленно — сравнивать будет
не с чем.

Инструмент: `scripts/rag_eval.py`. Старый `scripts/eval_retrieval.py` оставлен
для совместимости, но им мерить нельзя — почему, см. раздел «Почему старый eval
не годится».

## Шаг 0. Проверить, что контур вообще пригоден к замеру

```powershell
.\.venv\Scripts\python.exe scripts\rag_eval.py preflight
```

Скрипт печатает и проверяет:

- контракт эмбеддингов — какая модель запрошена и какую сервер реально отдал;
- манифест индекса — какой моделью, размерностью и чанкером собран стор;
- число проиндексированных чанков;
- наличие `metadata.db` по абсолютному пути;
- живой пробный запрос: статус трейса, каналы, слияние, шкала score
  и **parent context**.

Выход `READY TO MEASURE` — можно мерить. `NOT READY TO MEASURE` со списком
проблем — сначала чинить, потому что замер деградировавшего контура ничего
не значит.

**На что посмотреть в первую очередь.** В строке
`parent context in pool: hydrated=… fell_back_to_child=…`. Если `hydrated=0`,
значит `parent_chunks` не подтягивались и поиск всё это время строился на
child-чанках по 150 токенов вместо parent-контекста на 1000. До версии, где
путь к `metadata.db` резолвится от корня репозитория, так и было всегда, когда
MCP-сервер стартовал не из папки проекта — а Claude Desktop запускает его
именно так. Это тот случай, когда сначала имеет смысл переиндексации не делать,
а просто перезапустить сервер на новой версии и сравнить ответы.

## Шаг 1. Собрать кандидатов для golden-набора

```powershell
.\.venv\Scripts\python.exe scripts\rag_eval.py bootstrap `
    --questions golden\questions.json `
    --out golden\candidates.json `
    --k 8
```

`golden/questions.json` — стартовый набор из 16 вопросов, сформулированных так,
как их задаёт инженер, и **специально не содержащих** ни номеров норм, ни
доменных формулировок, которые мы ждём в ответе. Правьте его под свой корпус:
вопросы должны быть про то, что у вас реально проиндексировано.

Скрипт прогоняет вопросы и выписывает по каждому top-K с именем файла, разделом,
score и фрагментом текста.

## Шаг 2. Проверить источники руками

Это единственный шаг, который нельзя автоматизировать, и именно он делает
замер замером.

Откройте `golden/candidates.json`. Для каждого кейса:

1. Найдите среди кандидатов те файлы, которые **действительно** отвечают на
   вопрос. Откройте файл и убедитесь — не по имени, а по содержимому.
2. Впишите их в `source_any` (подстрока имени файла или пути; достаточно, чтобы
   хоть один нашёлся в top-K).
3. Если ответ обязан быть в самом верху — впишите тот же файл в
   `source_top_any` и задайте `source_top_k` (по умолчанию 3).
4. `must_find` — слова, которые обязаны встретиться в **тексте** найденного
   фрагмента. По умолчанию все они должны быть в одном чанке
   (`must_find_same_chunk: true`). Не пишите сюда номера норм, если они уже
   есть в `source_any` — это дублирование, а не проверка.
5. `forbid_sources` — файлы, которых в выдаче быть не должно. Так ловится
   утечка из соседнего датасета: проектный вопрос не должен отвечать нормативкой.
6. Поставьте `verified: true` и удалите блок `_candidates`.

Кейс, где нужного документа не нашлось вообще, — это не повод его выкинуть.
Это самый ценный кейс: запишите в `source_any` правильный файл (вы же знаете,
где ответ) и оставьте — он будет красным, пока retrieval его не достанет.

Сохраните результат как `golden/flying_rag_golden.json`.

## Шаг 3. Снять baseline

```powershell
.\.venv\Scripts\python.exe scripts\rag_eval.py run `
    --gold golden\flying_rag_golden.json `
    --k 5 --label baseline `
    --out scratch\eval\baseline.json
```

Скрипт **откажется** считать, если хоть один кейс не помечен `verified` или не
имеет источника: число, полученное из непроверенного набора, — не измерение.

По умолчанию включены три гейта, каждый отключается явным флагом:

| Гейт | Что делает | Как отключить |
| --- | --- | --- |
| `--require-source-verification` | отказ считать непроверенный набор | `--allow-unverified` |
| `--require-trace-ok` | `blocked`/`degraded` не получает проходной балл | `--allow-degraded` |
| `--require-parent-context` | выдача без parent-контекста не проходит | `--allow-child-only` |

Отключать их стоит только осознанно: они существуют ровно затем, чтобы
сломанный контур не выдавал правдоподобное число.

Сохраните `scratch/eval/baseline.json` — это точка отсчёта.

## Шаг 4. A/B

Сравнить два плеча на одном и том же индексе и наборе:

```powershell
.\.venv\Scripts\python.exe scripts\rag_eval.py ab `
    --gold golden\flying_rag_golden.json --k 5 `
    --out scratch\eval\ab_rerank.json
```

Встроенное A/B — реранк off против on. Для сравнения «до Волны 1 / после»
запускайте `run` на двух ревизиях кода с одним и тем же golden и одним и тем же
индексом, затем сравнивайте `passed`, `hit_rate@k`, `mrr` и `mean_precision@k`.

Метрики считаются **по источнику**, а не по вхождению слова в текст: попадание
засчитывается, если retrieval достал нужный документ. Это то, что нельзя
накрутить, дописав ожидаемое слово в запрос.

## Что смотреть в отчёте

В каждой строке кейса сохраняется дайджест трейса:

```
status, route, channels, fusion, score_kind, degraded,
parent_hydrated, parent_fell_back, rerank_status, rerank_head_changed, subqueries
```

Полезные сигналы:

- `fusion=none` и `channels=['dense']` при том, что гибрид запрашивался, —
  FTS-индекс не работает, лексический канал мёртв;
- `rerank_status=applied`, но `rerank_head_changed=false` на всех кейсах —
  реранкер ничего не переупорядочивает, его вклад нулевой;
- `parent_fell_back` больше нуля — часть выдачи идёт обрезанным контекстом;
- `subqueries` длиной больше единицы показывает, что именно дописал планировщик
  в запрос. Это прямо связано со следующим разделом.

## Почему старый eval не годится

`scripts/eval_retrieval.py` считал кейс пройденным, если ожидаемый термин
нашёлся где угодно в выдаче — включая имя файла. При этом `query_planner`
дописывал в подзапросы готовые доменные утверждения:

```
"Где нужна противодымная вентиляция?"
  → + "СП 7.13130 противодымная вентиляция дымоудаление требования"
```

а golden-кейс для этого же вопроса ожидал `["7.13130", "противодым"]`. То есть
мы клали в запрос ровно ту строку, которую потом искали в ответе. Зелёный
результат доказывал, что подстановка вернулась, а не что retrieval нашёл нужный
документ.

LES провели точно такой же аудит своего харнесса и оценили тестовую программу
на 4/10 именно за это (`docs/RAG_TEST_PROGRAM_AUDIT.md` в их репозитории):
«зелёный 16/16 не являлся доказательством retrieval quality». После чистки — 7/10.

Новый харнесс закрывает это тремя способами: релевантность судится по источнику,
`must_find` ищется только в тексте фрагмента, а вопросы в стартовом наборе не
содержат номеров норм — на это есть отдельный тест
(`test_rag_eval.ShippedQuestionsTests`).

Убирать подстановку из `query_planner` — пункт 09 плана
([LES_RESEARCH_2026-08-30.md](LES_RESEARCH_2026-08-30.md)). Он идёт первым
внутри Волны 1 именно потому, что baseline надо снять до него.

## Порядок

```
preflight  →  чинить, если не READY
bootstrap  →  проверить источники руками  →  golden
run        →  baseline (сохранить)
           →  правки Волны 1
run        →  сравнить с baseline
```
