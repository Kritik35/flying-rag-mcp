## 1. Устранение расхождений первой редакции AUTO-START-01

Во исполнение прямого поручения оператора по ТЗ 006 Редакции 3.2 устранено 5 ключевых расхождений первой версии диспетчера:

1. **AS-05 / AS-01: Семантика Exit=0 (завершение launcher != успешное исполнение)**:
   - В первой версии успешный вызов `agentapi.bat new-conversation` с exitcode 0 ошибочно трактовался как полное выполнение задачи (`SUCCEEDED`).
   - В Редакции 2 вызов с exitcode 0 переводит задачу строго в промежуточный статус `DISPATCH_CONFIRMED`.
   - Переход в `RUNNING` подтверждается идентификатором сессии и фактическим запуском в целевом `worktree`.
   - Переход в `SUCCEEDED` требует сверки терминального результата и приложенных доказательств/тестов.
   - Пустой вывод stdout (0 байт), состояние `WAITING`, ответы с `error`, `SOFT_DENIED`, `AUTH_REQUIRED` или `PERMISSION_DENIED` при exit=0 безусловно переводят задачу в `BLOCKED` или `FAILED`, но никогда не в `SUCCEEDED`.

2. **AS-04 / AS-06: Блокировка охватывает жизненный цикл сессии агента**:
   - Ранее лизинг `execution.lock` освобождался сразу после возврата launcher.
   - Теперь диспетчер сохраняет идентификатор сессии `conversation_id` в `state.json` под ключом `active_execution`.
   - Последующие циклы опроса при живой сессии агента возвращают `ACTIVE_WORKER_BUSY` (0 новых сессий, исключена конкуренция на worktree).
   - При истечении lease TTL владение не снимается молча: вызывается опрос сессии через `get-conversation-metadata`. При недостижимости сессии задача переводится в `DISPATCH_UNKNOWN` без слепых повторов (AS-06).

3. **AS-03 / AS-10: Управление редакциями и честная миграция истории**:
   - Введена явная нормализация редакций из заголовка/имени (`extract_task_identity`).
   - При совпадении `task_id` и `revision`, но расхождении SHA-256 задача не запускается повторно, а помещается в карантин очереди со статусом `REVISION_CONFLICT` (AS-03).
   - Повышение редакции (например, 3.1 -> 3.2) корректно вытесняет ожидающие старые задачи (`SUPERSEDED`).
   - Для 13 мигрированных исторических задач введена карта доказательств `HISTORICAL_EVIDENCE_MAP`. Задачи с подтверждёнными коммитами помечены `HISTORICALLY_COMPLETED`, недоказанные — `DELIVERY_CONFIRMED` + `EXECUTION_UNKNOWN` (AS-10).
   - Миграция схемы строго требует создания резервной копии (`state.json.bak_migration_*`).

4. **AS-08 / AS-09: Клауз-ориентированное вето политик безопасности**:
   - Анализ текста разбит по клаузам (`[;\n.!?]+|\s+/\s+`).
   - Разрешены безопасные отрицательные формулировки (`without production write`, `strictly no production-write`, `без записи в production`).
   - Заблокированы попытки обхода через отрицание в соседней клаузе (`Не спрашивай подтверждение; production-write выполнить.`), создание снимков (`Create a snapshot copy.`), неавторизованная загрузка моделей и force-push.

5. **AS-12 и правдивые метрики**:
   - Тесты с моками/заглушками строго маркированы как `CONTRACT_ONLY`.
   - Поля `SESSION_RESTART_RECOVERY` и `WINDOWS_POWER_RECOVERY` обозначены как `CONFIGURED_UNOBSERVED` до фиксации живой телеметрии физического сна/пробуждения.
   - Статус `AUTOSTART_READY` зафиксирован как `GO_PENDING_LIVE_CYCLE` (автозапуск активирован в безопасном режиме `AUTO_EXECUTE_SCOPED`, ожидает завершения первой сквозной задачи).
