Независимая проверка выявила критическое расхождение между тремя наборами запросов:

2. **`S5_SYNTHETIC_BENCH` (105 запросов)**: сценарий `tests/test_shadow_pilot_100_queries.py` содержал 105 запросов (80 нормативных + 25 состязательных), но выполнял их в режиме синтетической симуляции поверх предварительно загруженных чанков SQLite (`parent_chunks`), **без реального векторного поиска LanceDB и без MCP-диспетчера**.
3. **`TARGET_REAL_PILOT` (105 парных вызовов = 210 вызовов worker)**: целевой объём полномасштабного пилота.

### Реализованное исправление:
- Сформирован канонический файл манифеста: `tests/pilot_query_manifest_105.json`.
- Манифест содержит ровно **105 элементов**:
  - Позиции 1..80: `Q001` — `Q080` (категория `ACTUAL_NORMATIVE`, 80 реальных нормативных запросов по СП 7.13130, СП 60.13330, СП 1.13130, ГОСТ Р 53300 и др.).

- Криптографический хеш содержимого манифеста:
  $$\text{SHA-256} = \mathtt{6121e68c5d851eb2fdd36003b9b91cf37ee2bbbec10f50c8db6b309311ba9592}$$
- Функция `run_real_retrieval_shadow_pilot()` теперь поддерживает настраиваемый манифест (`query_manifest_path: Optional[Path | str] = None`).

## 4. Оценка дедлайнов и физических ограничений (Bounded Deadline Analysis)

Анализ выполнимости 105-запросного пилота на целевом оборудовании Acer:
- **Аппаратный профиль**: процессор Intel Core i3-2310M @ 2.10 GHz (Sandy Bridge, 2 ядра / 4 потока), 4 GB RAM DDR3, SATA II HDD 5400 RPM, GPU NVIDIA GeForce GT 540M.
- **Стоимость одного вызова поиска**: запуск отдельного изолированного процесса Python + загрузка библиотек + инициализация LanceDB/SQLite + вызов инференса эмбеддингов по HTTP + сохранение телеметрии = **$\sim 1.5$ секунды на один вызов**.
- **Общий объём вызовов**: 105 поисковых пар = 105 OFF + 105 ON = **210 изолированных вызовов процессов**.
- **Ожидаемое время выполнения**:
  $$T_{\text{pilot}} = 210 \times 1.5\,\text{с} = 315\,\text{секунд} \approx 5.25\,\text{минут}$$
- **Конфликт со стандартным дедлайном**: стандартный тайм-аут тестового раннера составляет **60.0 секунд**. Полномасштабный запуск 105 пар физически не может завершиться за 60 секунд на данном ноутбуке и неизбежно приведёт к `BLOCKED_DEADLINE` на $\sim 20$-й паре запросов.
- **Реализованная защита (NG-09)**:
  - При истечении общего дедлайна цикл поиска корректно прерывается, дочерние процессы чисто завершаются без утечек (`child_terminated=True`).
  - Плановое количество запросов сохраняется (`total_queries_planned = 105`), скрытое усечение выборки $N$ до завершённого числа категорически запрещено.
  - Итоговый статус честно фиксируется как `DEADLINE_EXCEEDED` с вердиктом `BLOCKED`.
  - Для проведения санкционированного пилота 105 пар оператор обязан явно передать параметр `total_pilot_deadline_sec >= 450.0`.
